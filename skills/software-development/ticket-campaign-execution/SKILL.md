# Ticket Campaign Execution

Оркестратор ведёт кампанию: спека и граф тикетов уже опубликованы в трекере репо (обычно GitHub Issues через `gh`), тикеты закрываются по фронтиру зависимостей с одним писателем на тикет. Триггеры: «закрой граф #N–#M», goal-промпт кампании, «делаем все эти штуки, декомпозируй» при готовой спеке. Одна задача без графа — это `cli-agent-first`, не кампания.

## Предусловия

1. Канон кампании читается в рабочем дереве до первого тикета: `AGENTS.md`, `CONTEXT.md`, тело спеки (`gh issue view <spec> --json body`). Авторитет — тело тикета и спека, не память сессии.
2. Свой worktree создан от нужной головы и прикреплён к Hermes-проекту; параллельные фронты — отдельные worktree.
3. Писатель проверен живьём: статус логина и пин модели в каталоге (`agent status`, `agent models`) до первого запуска.

## Контур одного тикета

1. **Фронт** — тикет с нулём открытых блокеров. Живой запрос: `gh api "repos/<o>/<r>/issues?labels=ready-for-agent&state=open"` и поле `issue_dependencies_summary.blocked_by` (оно есть только в REST-списке, не в `gh issue view`).
2. **Клейм** — `gh issue edit <n> --add-assignee @me`. Готово когда ассайн виден в выдаче трекера.
3. **Бриф в файл** по `templates/work-order-brief.md`: цель из тела тикета, инварианты из спеки, шаги с проверяемыми критериями готовности, именованный прогон приёмки. Текст брифа писать через `writing-for-agents`.
4. **Писатель** — один на тикет, промпт файлом. Выбор руки — `cli-agent-first` (UI/фронт — Cursor, необратимое/цена ошибки — Codex), запуск — скилл руки, модель пинить всегда.
5. **Приёмка** — полный дифф читается самому, именованный прогон гонится самому. Отчёт писателя не пруф; зелёный прогон писателя не равен зелёному прогону оркестратора. Для UI-тикетов визуальные снимки проверяются глазами (vision по снимкам из `docs/evidence`).
6. **Возврат** — не-зелёный прогон или расхождение с телом: возврат писателю с точной ошибкой и решением. Максимум два честных возврата, затем стоп с отчётом; писатель молча не подменяется другим.
7. **Закрытие** — комментарий-пруф: что прочитано в диффе + команда и фактический вывод собственного прогона. Затем `gh issue close`. Готово когда у зависимого тикета обнулились блокеры.

Пока писатель работает, пишутся брифы следующих тикетов фронта — старт без паузы после приёмки.

## Инварианты

- Один писатель на worktree; связанные исходы — один писатель, независимые фронты — разные worktree плоско.
- Никаких коммитов, пушей, деплоев до отдельного слова владельца; всё остаётся локальным диффом.
- Секреты и инвентари деплоя не читаются; живые чужие деплои не трогаются.
- Чужой смысл тестов не подгоняется; переворот закреплённого поведения — осознанно и с объяснением в брифе.

## Приёмка и флейки

Именованные прогоны для UI-фронта обычно двойные: гейт репо дважды подряд, оба зелёные. Визуальные баселайны — главный источник расхождений между прогоном писателя и своим: диагностика и паттерн детерминированного снимка в `references/acceptance-and-flakes.md`. Публикация в трекер имеет свои грабли (пустое тело, числовые id блокировок) — там же.

## Проверка кампании

- Каждый закрытый тикет имеет комментарий с выводом прогона оркестратора, не писателя.
- Фронт сдвигается: живые блокеры зависимых тикетов обнуляются.
- Ветка без коммитов (пока нет разрешения); дерево не тронуто вторым писателем.
- Финальный тикет кампании — один формальный `code-review` поверх всей ветки, находки исправлены, затронутые прогоны повторены.
