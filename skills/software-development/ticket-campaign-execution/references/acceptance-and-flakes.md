# Приёмка, флейки и грабли публикации

## Двойной прогон гейта

Для фронтенда с визуальными баселайнами один зелёный прогон — слабое доказательство: снимки недетерминированы между запусками (анимации, кадр плеера, буфер-индикатор, скелетоны). Стандарт приёмки — `make <frontend-gate>` (или эквивалент) **дважды подряд**, оба зелёные. Писатель гонит сам два раза; оркестратор гонит свой раз после чтения диффа. Зелёный прогон писателя и красный свой — это возврат №1, а не флейк по умолчанию.

## Диагностика визуального регресса

Порядок при `visual regression for <name>`:

1. Открыть `<actual>.diff.png` через vision: вопрос «какие области отличаются, геометрия изменений».
2. Одна компактная точечная область — недетерминированный кадр (курсор, буфер-индикатор, первая фаза анимации, недогруженные метаданные плеера). Крупные блоки/полосы — реальное изменение раскладки.
3. Фикс — стабилизация кадра **в тесте**, не в приложении: перед `capture_evidence` ждать детерминированное состояние (видимость ключевого контента, `readyState`/`canplay` у видео, отсутствие оверлеев загрузки/ошибки), затем принудительно скрыть плавающие индикаторы (`display:none !important` на буфер-спиннерах).
4. Перегенерация баселайнов — только после стабилизации кадра (в репо обычно `UPDATE_<NAME>_BASELINES=1`-переменная, см. `Makefile`).
5. Особый класс: тест-фикстура с мусорным медиа. Если встреча переводится в READY напрямую через SQL без артефактов, плеер крутит недодекодированный файл и кадр гуляет. Правильный фикс — публиковать настоящий транскрипт и воспроизводимый MP4 через реальный конвейер, затем возвращать статус в начальное состояние для живого перехода.

## Чтение накопительного диффа

В кампании без коммитов `git diff` — накопительный по всем закрытым тикетам. Оценивать дельту текущего тикета по `git diff --stat` и перечню файлов из брифа, а не по полному диффу. Бинарные снимки (`docs/evidence/**`) в `--stat` исключать: `git diff --stat -- ':(exclude)docs/evidence'`.

## Грабли публикации в GitHub-трекер

- `gh issue create --body` с большим телом через heredoc может прийти **пустым** (`gh issue view <n> --json body --jq '.body' | wc -c` вернёт 1). Лечится переписыванием через `gh issue edit <n> --body-file <файл>`. Все публикации безопаснее делать `--body-file`.
- Нативные блокировки: `gh api --method POST repos/<o>/<r>/issues/<child>/dependencies/blocked_by -F issue_id=<db-id>`, где `db-id` — числовой `gh api repos/<o>/<r>/issues/<n> --jq .id`, не номер и не `node_id`.
- Живое число открытых блокеров — `issue_dependencies_summary.blocked_by` в REST-списке задач. Поле отсутствует в `gh issue view --json` (там «Unknown JSON field») — только через `gh api` списком.
- Авторизация: в сессиях профилей `gh` часто не залогинен; рабочий логин лежит в `~/.config/gh/hosts.yml` — префикс `GH_CONFIG_DIR=/home/<user>/.config/gh` на каждую команду.

## Что писать в комментарий-пруф при закрытии

1. Что прочитано в диффе (по пунктам приёмки тикета, а не «всё ок»).
2. Осознанные отклонения от брифа, если были, и почему они допустимы.
3. Прогоны писателя (хвосты) и **свой** прогон: команда и фактический вывод.
4. Явное «коммитов нет — локальный дифф в <ветка>», пока нет разрешения владельца.
